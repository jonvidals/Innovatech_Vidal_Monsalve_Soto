Actividad: Implementación, despliegue y validación de una aplicación en Amazon EKS
En esta actividad, las y los estudiantes deberán implementar una solución completa de orquestación de contenedores utilizando Amazon EKS, abarcando desde la creación del clúster hasta el despliegue, escalamiento y monitoreo de una aplicación multicapa contenerizada.
La actividad contempla la creación de un clúster EKS y sus Node Groups, la configuración de acceso mediante kubectl, la actualización y publicación de imágenes Docker en Amazon ECR, y el despliegue de la aplicación utilizando manifiestos YAML de Kubernetes (Deployments, Services, namespaces y secretos).
Posteriormente, las y los estudiantes deberán validar el correcto funcionamiento de la aplicación, exponiéndola mediante un Service de tipo LoadBalancer, y comprobar su acceso desde el navegador. Como parte del proceso, se abordará la implementación de escalamiento automático (HPA), la tolerancia a fallos (auto-healing) y la observabilidad del clúster, utilizando métricas de Kubernetes y logs del plano de control en Amazon CloudWatch.
Esta actividad permite integrar de forma práctica los conceptos de contenedorización, orquestación, CI/CD y operación de aplicaciones en Kubernetes, reforzando competencias clave de DevOps, alta disponibilidad, escalabilidad y monitoreo en entornos cloud basados en AWS.
Crear un clúster Amazon EKS: componentes y flujo:
Crear clúster EKS
Seleccionar VPC y subredes (públicas para ALB, privadas para nodos).
AWS crea y administra el Control Plane.
2. Crear Node Group
EC2 administrados por autoscaling.
Se asignan roles IAM para permitir la ejecución de pods.
3. Conectar kubectl
Ejecutar en local Aws configure
Descargar kubeconfig.
Verificar nodos: kubectl get nodes
4. Actualizar imagen en ECR
Login, Build, tag, y push versión eks-v1
5. Desplegar aplicación
Crear Deployment + Service.
Desplegar Load Balancer a través de Service.
Validar aplicación web del proyecto por dns balanceador.
6. Escalado y Monitoreo
Validar HPA y tolerancia a fallas.
Ver métricas en CloudWatch.

Actividad 4: Validar escalamiento y monitoreo EKS
PASO 1: Desplegar HPA
En la carpeta /k8s del proyecto en CMD ejecutar:
kubectl apply -f backend-hpa.yaml
kubectl apply -f frontend-hpa.yaml
kubectl get hpa -n tienda
PASO 2: VALIDAR HPA (Horizontal Pod Autoscaler)
Ver si el HPA está leyendo métricas correctamente
kubectl get hpa -n tienda
PASO 3: Generar carga para obligar al HPA a escalar
 Ubicar un pod del backend:
kubectl get pods -n tienda -l app=tienda-backend
 Entrar al pod:
kubectl exec -it <nombre-del-pod> -n tienda -- sh
 Instalar curl (si no está):
apk add --no-cache curl
Ejecutar un loop de carga:
while true; do curl -s http://localhost:3001/api/productos > /dev/null; done
Este loop sube el uso de CPU para activar el HPA.
Desde otra terminal CMD, ver el escalado:
kubectl get hpa -n tienda -w
Ejemplo esperado:
tienda-backend-hpa Deployment/tienda-backend 82%/70%  2   10   3
tienda-backend-hpa Deployment/tienda-backend 95%/70%  2   10   4
El HPA pasa de 2 → 3 → 4 réplicas según carga.
Ver pods nuevos:
kubectl get pods -n tienda -l app=tienda-backend
PASO 4: Detener la carga y ver cómo baja
En el pod que ejecuta el loop presiona:
Ctrl + C
Revisa cómo baja el target:
kubectl get hpa -n tienda -w
Ejemplo:
tienda-backend-hpa   Deployment/tienda-backend  23%/70% 2-10 4→3→2
HPA vuelve a las réplicas mínimas.
PASO 5: VALIDAR TOLERANCIA A FALLAS (AUTO-HEALING)
Kubernetes siempre repara pods que fallan, gracias a:
livenessProbe
readinessProbe
Deployment ReplicaSet
2.1 Obtener pods actuales del backend
kubectl get pods -n tienda -l app=tienda-backend
Ejemplo:
tienda-backend-7d877f4457-lj2tc
tienda-backend-7d877f4457-xf2ml
PASO 6: Eliminar un pod para ver auto-healing
kubectl delete pod tienda-backend-7d877f4457-lj2tc -n tienda
Resultado:
pod "tienda-backend-xxxx" deleted
Automáticamente aparece otro:
kubectl get pods -n tienda -l app=tienda-backend -w
Ejemplo verás:
tienda-backend-7d877f4457-lj2tc   Terminating
tienda-backend-7d877f4457-abc12   Running
El ReplicaSet creó un pod nuevo = TOLERANCIA A FALLAS OK
PASO 7: Simular fallas del Contenedor (Kill dentro del pod)
Entra al pod:
kubectl exec -it <pod-backend> -n tienda -- sh
Mata el proceso:
kill 1
(Kubernetes detecta livenessProbe fallida → reinicia el contenedor)
Ver estados:
kubectl get pods -n tienda -l app=tienda-backend
Verás RestartCount > 0:
kubectl describe pod <pod> -n tienda | grep Restart
PASO 8: VALIDAR MÉTRICAS (kubectl + CloudWatch)
Ver uso de CPU y RAM desde kubectl (metrics-server)
kubectl top nodes
kubectl top pods -n tienda
Ejemplo:
NAME                     CPU(cores)   MEMORY(bytes)
ip-10-0-1-20.ec2...      220m         410Mi
ip-10-0-2-15.ec2...       70m         230Mi
NAME                                   CPU   MEM
tienda-backend-7d877f4457-lj2tc        110m  95Mi
tienda-frontend-6789df4c8f-ptk7j       5m    10Mi
Si ves esto → metrics-server está funcionando.
PASO 9: CloudWatch Logs (Control Plane)
 Ir a CloudWatch → Logs → Log groups
 Buscar:
/aws/eks/nombre-cluster-eks/cluster
Aquí encontrarás:
kube-apiserver
audit
scheduler
controllerManager
Seleccionar uno de los logs y revisar. Aporta visibilidad del clúster.

Actividad: Construcción del Pipeline CI/CD para despliegue en Amazon EKS
En esta actividad, las y los estudiantes deberán diseñar e implementar un pipeline de Integración y Entrega Continua (CI/CD) utilizando GitHub Actions, con el objetivo de automatizar la construcción, publicación y despliegue de una aplicación contenerizada en Amazon EKS.
La actividad contempla la creación de un repositorio en GitHub, la subida del proyecto estructurado por capas (frontend, backend y base de datos), la configuración de secretos y variables de entorno para la integración segura con AWS, y la definición de un workflow CI/CD que incluya etapas de build de imágenes Docker, push a Amazon ECR y despliegue en el clúster EKS mediante kubectl.
Como resultado, las y los estudiantes deberán visualizar la estructura completa del pipeline CI/CD, validar su correcta ejecución ante cambios en el código y comprender cómo GitHub Actions permite automatizar despliegues reproducibles, trazables y alineados con prácticas DevOps en entornos cloud basados en Kubernetes.

build

PASO 6
Entender la lógica de cada pipeline
Cada pipeline (workflow) sigue exactamente la misma estructura lógica, variando solo los nombres de la capa y los secretos utilizados. Entender esta lógica es fundamental para el examen.
6.1 — Estructura de un pipeline
Etapa
¿Qué hace?
Trigger (on: push)
El pipeline se activa automáticamente cuando se hace git push a main Y hay cambios en la carpeta de esa capa (db/**, backend/**, frontend/**). Si cambias backend/, solo se ejecuta el pipeline del backend.
checkout
El runner (servidor temporal de GitHub) descarga el código del repositorio para poder trabajar con él.
configure-aws-credentials
Configura las credenciales de AWS usando los secretos. A partir de aquí, todos los comandos AWS funcionan autenticados.
amazon-ecr-login
Hace login en el servicio Amazon ECR (Elastic Container Registry) desde el runner. ECR es el registro privado de imágenes Docker de AWS.
docker build
Construye la imagen Docker usando el Dockerfile de la capa correspondiente.
docker tag + docker push
Etiqueta la imagen con la URL del repositorio ECR y la sube al registro.
ssm send-command
Envía un comando de shell a la instancia EC2 correspondiente a través del servicio SSM (Systems Manager). EC2 ejecuta ese comando remotamente, sin que el runner tenga acceso directo por SSH.
Dentro del comando SSM
En la EC2: hace login en ECR, descarga la nueva imagen (docker pull), detiene y elimina el contenedor anterior, y lanza el nuevo contenedor con la imagen actualizada.
